# Agent 效果优化：诊断 + 已验证的三个改动

> 全部基于同一批 50 条样本（`data/dataset/eval.json`）、同一模型（`deepseek-flash`）、
> 同一口径（行号级：类别相同且行号落在标注 ±1 内）。
> 结论都可复现：`experiments/exp_agent_prompt_variants.py`、`experiments/diagnose_fps.py`。

---

## 0. 三句话结论

1. **Agent 不是"看不准"，是"报太多"**：94 个问题命中 45 个（召回 0.90），但平均每样本报
   2.14 条而标注只有 1.0 条，多出来的都算误报。
2. **误报里 77% 是"标注没这一类"而不是"行号错了"**（62 个 FP：48 个跨类别 / 14 个行号错），
   其中 44 个是代码坏味、26 个是"命名不规范"——这些内容本身不算错，只是不在评测任务范围内。
3. **三个不改模型的改动，把 F1 从 0.542 拉到 0.699**（+0.157），代价是 token +65%；
   再加一层置信度过滤能到 0.648（单独使用时）。

---

## 1. 诊断：误报花在哪了

### 1.1 数量对比

| | 值 |
|---|---|
| 每样本标注数 | 1.00 |
| Agent 每样本报出 | 2.14 |
| 命中 / 漏报 | 45 / 5 |
| 误报 | 62 |

召回 0.90 已经不低（原生 LLM 也是 0.92）。**瓶颈完全在精确率 0.42。**

### 1.2 误报归因

| 类型 | 数量 | 含义 |
|---|---|---|
| 类别对、行号超容差 | 14 | 定位精度问题（真·错） |
| **类别不在标注里** | **48** | 报了这个样本没标注的问题类别 |

按类别：`smell` 44 / `bug` 16 / `security` 1 / `performance` 1。
按二级类型前五：命名不规范 26、魔术数字 6、死代码 6、未使用变量/导入 5、边界条件 5。
按置信度：<0.6 有 27 个、0.6–0.8 有 14 个、≥0.8 有 21 个。
按证据来源：**62/62 全部带工具证据**。

两个直接推论：

- **证据闭环不是精确率工具。** 100% 的误报都能挂上工具证据，说明"有证据"挡不住"报多了"。
  它防的是幻觉，不是判断口径。
- **坏味类（尤其命名）是主要噪声源。** 43/62 集中在这里，且这类问题按定义就是"主观建议"。

### 1.3 一个具体例子

```
DATA-PY-99   smell/Non-Standard Naming  line 1-8  conf 0.70
  函数 calc_result 未提供任何 docstring 或说明性注释，无法从代码得知累加 0..99 的业务意图
```

这条不算胡说，但数据集标的是该样本的**安全漏洞**，于是它被记成 FP。这类"合理但越界"的
输出占了误报的大头——**所以先别急着改模型，先改"什么时候该闭嘴"。**

## 2. 三个改动 + 实测效果

`core/reviewer.py` 的提示词是 `ROLE + RULES + REVIEW_STEPS + FEW_SHOT_EXAMPLES + 代码 + 格式`；
`agent/reviewer_agent.py` 的 system prompt 只有 `ROLE + RULES + Agent 工作流 + JSON 格式`，
**少了两块**。而 `exp2a` 的消融早就量过这两块最值钱（去 few-shot −0.081，去链式推理 −0.032）。

于是在同一批样本上把这两块补回去，并测试一个"数量约束"：

| 变体 | P | R | F1 | 报出条数/样本 | 平均步数 | token/样本 | 耗时/样本 |
|---|---|---|---|---|---|---|---|
| v0 现状 | 0.400 | 0.840 | 0.542 | 2.10 | 6.44 | 10,391 | 14.6s |
| v1 + `REVIEW_STEPS` | 0.500 | 0.800 | 0.615 | 1.60 | 5.94 | 10,944 | 13.6s |
| v2 + `FEW_SHOT_EXAMPLES` | 0.585 | 0.760 | 0.661 | 1.30 | 5.72 | 17,003 | 11.3s |
| v3 + 两者 | 0.567 | 0.760 | 0.650 | 1.34 | 5.38 | 17,660 | 12.5s |
| **v4 + 两者 + 数量约束** | **0.679** | 0.720 | **0.699** | **1.06** | 5.26 | 17,181 | 10.7s |

v4 加的那段约束（原文）：

```
【数量约束（硬性）】
- 单次审查最多输出 3 条问题；同一 category 最多 2 条。
- confidence 低于 0.75 的条目不要输出——把它当作"我没把握"，宁可不报。
- 如果静态分析工具没有任何命中，且你也找不到可复现的触发路径，输出空 issues 数组是正确的答案。
```

读法：

- **few-shot 单项收益最大（+0.119）**，和 exp2a 的结论一致；代价是 token +64%。
- **加了约束后反而更快**（14.6s → 10.7s），因为少报几条、少绕几步。
- 精度从 0.400 到 0.679，召回只从 0.840 掉到 0.720——**这是净赚**。
- v3 < v2 属于 50 条样本上的噪声（基线三次重复的 F1 分别是 0.542 / 0.573 / 0.586，
  所以 ±0.04 以内的差异别当真）。

## 3. 置信度过滤：不依赖模型自觉的兜底

模型写"宁可不报"是软的。真正可靠的是在 finalizer 里按 `confidence` 删：

| 阈值 | 保留条数 | P | R | F1 |
|---|---|---|---|---|
| 不过滤 | 107 | 0.421 | 0.900 | 0.573 |
| 0.60 | 74 | 0.527 | 0.780 | 0.629 |
| 0.70 | 67 | 0.537 | 0.720 | 0.615 |
| 0.75 | 61 | 0.574 | 0.700 | 0.631 |
| **0.80** | 55 | 0.618 | 0.680 | **0.648** |
| 0.85 | 46 | 0.652 | 0.600 | 0.625 |
| 0.90 | 39 | 0.718 | 0.560 | 0.629 |

**0.80 是最优拐点，单独用就能 +0.075。** 注意这是在同一批数据上挑的阈值（in-sample），
真实部署建议取 0.75–0.80 并在验证集上确认。

实现位置：`agent/reviewer_agent.py` 的 `_ReportFinalizer._verify_and_filter`，
在末尾加一句 `kept = [i for i in kept.issues if i.confidence >= threshold]` 即可，
阈值走 `EvidencePolicy` 配置项（已有 `min_confidence_without_tool`，可再加一个全局下限）。

## 4. 成本更高、但值得排期的结构改动

按「预期收益 / 工程量」排序：

| 改动 | 思路 | 收益预期 | 代价 |
|---|---|---|---|
| **A. 坏味降权** | 命名/魔术数/死代码这类默认只进「建议」区，不计入 issues；或整类默认关闭 | 直接砍掉 43/62 的 FP | 极小 |
| **B. 让 `core.reviewer` 当 verifier** | Agent 提候选 → core 的规则+单次调用复核 → 只留交集或高置信 | exp1 里 core 的 P=0.703，做筛子很合适 | 中（多一次调用） |
| **C. 多智能体 Critic** | 复用现成的 `--mode multi` | 未知，需实测 | 高（调用翻倍） |
| **D. 改评测口径** | 改成 Top-K 命中 或 多标签"额外发现不计 FP" | 让分数反映真实能力 | 中（历史结果不可比） |

**关于 D**：这个数据集的 1 条/样本标注，本质上是"找出唯一那个预设问题"，
在这种口径下"每样本只报 1 条"永远最优。如果项目的卖点是"审查助手"，
用 F1 衡量本身就会低估它——但换口径必须有旧数据不可比的心理准备。

---

## 5. 建议的实施顺序

1. **先上 v4**（few-shot + REVIEW_STEPS + 数量约束）：改一个字符串，+0.157，已验证。
2. **再加 confidence ≥ 0.75 的 finalizer 过滤**：几行代码，把"模型不听话"兜住。
3. **然后做 A（坏味降权）**：把 FP 的大头从源头掐掉，预计能再往 0.72–0.75 走。
4. **有余力再做 B**，C 只在 D 的方案确定后再考虑。
